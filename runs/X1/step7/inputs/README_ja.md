# CCS26 Step 7 — 翻訳器が行IDの条件を生成する候補

前の候補版の `Rule.hs`（SHA-256 `ccf63a271655fd1900a990a4a54be6ce28ebf26b26dc198e74ca9f0a29871d2c`）を起点に、同じ線形テーブルを1つの MSR 規則で複数回読む場合の生成処理を追加した。差分は `row-id-guards.patch`、ビルド対象は `context/Rule.candidate.hs`。

後続の `get` に、同じテーブルの先行するすべての行IDとの不等号条件を付ける。パターン付き取得と単純取得を翻訳器の既存の出力順で扱う。永続事実の取得、既存の `DistinctFact` 制約、埋め込み規則の翻訳経路には変更を加えない。

Step 3 の記録にある Dockerfile フロントエンドとビルドベースのダイジェストを使用する。初回やキャッシュ破棄後には、ソースとビルド依存物の取得が発生する。新候補を別ディレクトリにビルドし、実行フェーズで固定イメージと工具のハッシュを照合する。各検証コマンドは60秒、コンテナは1 CPU・2 GiB、ネットワーク無効。

## WSL で実行する

ZIPを展開し、このディレクトリで以下を実行する。

```bash
sha256sum -c SHA256SUMS &&
bash run-step7.sh
```

| 試験モデル | 補題数 | 点検内容 |
|---|---:|---|
| linear_pair | 2 | 自動生成したPVと Step 6 の条件付きPVを、空白とビルド情報を除いて照合 |
| linear_triple | 2 | 3個の読みで、後続の読みがすべての先行行IDと異なるように生成 |
| linear_mixed | 2 | パターン付き取得と単純取得の間でも条件が生成される |
| linear_plain | 2 | 単純取得だけの規則でも条件が生成される |
| persistent_pair | 1 | 1件の永続事実を2回読む正例が成立し、行ID条件が付かない |

直接検証、翻訳、ProVerif の判定に加えて、線形の正例では復元トレースで取得行を照合する。`decision=PASS`、`MATCH=9`、`stage=complete`、`rc=0` がこの試験の完了条件。

停止時を含め、`ARCHIVE=` が示すアーカイブにビルドログ、ソースの差分、生成されたモデル、判定と原ログが入る。実行成功後は `CANDIDATE_BINARY=` が指すファイルを保持する。回帰試験で再利用する。

配布前に行った確認は、元候補のソースへの差分適用、既存の実測出力を用いた検査処理、Docker呼び出しを模擬した収録経路。新候補の実コンパイルと新規モデルの検証は、このキットを実行して確認する。
